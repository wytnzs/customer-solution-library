# 客户管理库操作手册

> 面向使用者和 Agent 的说明。  
> 这份手册回答三个核心问题：这套客户管理库是什么、怎么用、为什么要这样构建。

---

## 1. 这套客户管理库是什么

客户管理库不是传统 CRM，也不是普通通讯录或 Excel 表格。

它是一套面向长期客户服务的「客户信息管理与解决方案系统」：

```text
客户信息
→ 价值判断
→ 客户匹配
→ 档案沉淀
→ 客户分析
→ 专属方案
→ 跟进复盘
```

它的目标不是简单地“存客户”，而是让 Agent 帮你持续回答：

- 这个客户是谁？
- 他/她发生过什么？
- 现在处在什么状态？
- 哪些信息是事实，哪些只是推断？
- 当前最重要的风险、需求和机会是什么？
- 下一步应该如何跟进？
- 能否基于已有信息生成专属解决方案？
- 如果现在要推某个产品/服务，哪些客户最可能匹配？

因此，它更像一个「客户长期服务大脑」。

你可以把聊天记录、录音转写、面谈纪要、客户口述、保单资料、健康告知、方案沟通、团队反馈等信息交给 Agent，由 Agent 按统一规则整理为：

- 客户主档案
- 客户事件流
- 业务模块资料
- 客户分析 brief
- 专属解决方案草稿
- 跟进动作
- 团队协同摘要
- 数据质量报告
- 产品潜在客户清单
- 本周经营看板

重要提醒：

本系统的真实客户资料应放在你自己的私有客户库中。当前 GitHub 仓库只提供规则、模板、脚本和 Skill，不保存真实客户数据。

---

## 2. 为什么要这样构建

真实客户服务有一个特点：信息不是一次性完整出现的，而是不断从沟通中累积出来的。

例如：

- 第一次只知道客户想了解保险。
- 第二次补充了家庭结构。
- 第三次发来体检异常。
- 第四次提供已有保单。
- 第五次开始讨论方案。
- 后续又出现缴费、理赔、加保、家庭变化等新情况。

如果用传统表格管理，很容易出现三个问题：

1. 表格字段太固定，放不下复杂上下文。
2. 聊天、录音、资料、判断过程分散在不同地方。
3. 客户越多，信息越难检索、复盘和交接。

所以这套客户管理库采用 Markdown + YAML + 事件流 + 索引 + Agent 的结构。

它的设计思路是：

```text
Markdown：保存长文本、上下文、沟通过程
YAML：保存客户编号、状态、标签、阶段等结构化字段
事件流：保存客户信息变化的历史过程
主档案：保存当前稳定摘要
索引：支持快速查找、筛选和质检
Agent：负责摘录、分析、匹配、更新、生成方案
洞察层：负责需求、风险、机会、顾虑、信息缺口
经营层：负责产品匹配、客户筛选、跟进看板
```

这样的好处是：

- 信息可以先进入入口池，不必一开始就整理完美。
- Agent 可以先判断信息价值，避免客户库变成垃圾箱。
- 同名客户不会因为名字相同就被误合并。
- 客户主档案保持简洁稳定，历史细节放在事件流。
- 后续可以自然扩展到团队协同、复核、脱敏和交接。
- 客户信息可以沉淀为长期可复用的服务资产。
- 可以从“某个产品/服务”反向筛选客户，形成真正可行动的经营清单。

## 3. 最小计量单位

这套系统的最小计量单位不是“客户”，而是“客户信息事件”。

传统方式常常这样理解：

```text
一个客户 = 一条记录
```

但在长期服务中，更合理的理解是：

```text
一个客户 = 多个客户信息事件不断累积后的当前画像
```

客户信息事件可以是：

- 一段聊天记录
- 一段录音转写
- 一次面谈纪要
- 一条客户口述
- 一份资料补充
- 一个健康异常信息
- 一次保单变化
- 一次方案沟通
- 一个跟进动作
- 一次团队反馈

每条客户信息事件至少要尽量说明：

| 问题 | 说明 |
|---|---|
| 来源是什么 | 微信、电话、录音、面谈、资料、团队反馈等 |
| 时间是什么 | 这条信息什么时候发生或被记录 |
| 关联谁 | 已知客户、疑似客户，或暂时待匹配 |
| 价值多高 | 是否值得进入客户档案或后续跟进 |
| 是否改变判断 | 是否影响客户画像、风险、需求、方案 |
| 下一步是什么 | 是否需要补资料、预约、出方案、提醒、复核 |

为什么不用“客户”作为最小单位？

因为客户主档案应该是稳定摘要，不应该把所有聊天细节都堆进去。

正确结构是：

```text
客户主档案 = 当前稳定摘要
客户事件流 = 历史过程
业务模块 = 不同业务线的专属资料
方案与分析 = 阶段性判断和输出
跟进记录 = 下一步动作和服务节奏
```

这样即使客户数量达到几千、上万，系统也不会因为资料不断增加而变得混乱。

## 4. 怎么用

### 4.1 一条指令安装

Windows PowerShell：

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\.codex\skills" | Out-Null; git clone https://github.com/wytnzs/customer-solution-library.git "$env:USERPROFILE\.codex\skills\customer-solution-library"
```

macOS / Linux：

```bash
mkdir -p ~/.codex/skills && git clone https://github.com/wytnzs/customer-solution-library.git ~/.codex/skills/customer-solution-library
```

安装后，你可以对 Agent 说：

```text
使用 $customer-solution-library，帮我初始化并管理客户库。
```

### 4.2 第一次使用：初始化客户库

客户库是你真正保存客户资料的地方。建议单独放在一个私有目录中，例如：

```text
D:\Claude\客户解决方案库-私有
```

你可以让 Agent 初始化，也可以手动运行：

```powershell
python scripts/customer_library.py init --base D:\Claude\客户解决方案库-私有
```

初始化后，会形成一套标准目录，用来分别存放入口信息、客户档案、事件流、业务模块、方案分析、团队协同、服务跟进、索引看板和模板规则。

### 4.3 日常使用：一步操作

大多数时候，你只需要把客户信息交给 Agent。

例如：

```text
使用 $customer-solution-library。
客户库路径是 D:\Claude\客户解决方案库-私有。

请处理这条客户信息：
张先生，杭州，李姐转介绍，已婚一孩，想了解重疾险，最近体检发现甲状腺结节，周五晚上有空。
```

Agent 会按规则完成：

- 判断这条信息是否有价值。
- 搜索是否已有对应客户。
- 检查是否存在同名客户风险。
- 能确认客户时写入客户事件流。
- 更新客户主档案摘要。
- 更新相关业务模块。
- 设置下一步动作。
- 刷新索引。

你也可以这样说：

```text
整理这段客户聊天记录并入库：……
```

或者：

```text
根据这个客户最近三次沟通，生成客户分析 brief 和下一步跟进建议。
```

或者：

```text
检查客户库健康状态，列出缺少下一步动作、疑似重复、待匹配、隐私风险的信息。
```

### 4.4 高风险信息：三步操作

如果客户信息很重要、很敏感，或者可能存在同名误匹配，建议使用三步操作。

第一步：只判断价值，不入库。

```text
先只判断这段客户信息的价值，不要入库：……
```

第二步：只匹配客户，不写入。

```text
根据上面的信息，帮我匹配可能客户，但先不要写入。
```

第三步：确认后正式入档。

```text
确认是 CUST-0001，请正式入库，并更新摘要、事件流和下一步动作。
```

三步操作适合：

- 同名客户
- 健康告知
- 理赔、投诉、纠纷
- 保单变更
- 重要承诺
- 团队交接
- 客户隐私信息
- 任何你不希望 Agent 自动判断错误的情况

### 4.5 常用功能

判断一段信息是否值得入库：

```powershell
python scripts/customer_library.py score-intake --text "张先生说孩子刚上小学，最近体检发现甲状腺结节，想看看重疾险，周五晚上有空。"
```

搜索客户：

```powershell
python scripts/customer_library.py find --base D:\Claude\客户解决方案库-私有 --query 张先生
```

刷新索引：

```powershell
python scripts/customer_library.py index --base D:\Claude\客户解决方案库-私有
```

生成数据质量报告：

```powershell
python scripts/customer_library.py audit --base D:\Claude\客户解决方案库-私有
```

生成客户深度分析：

```powershell
python scripts/customer_library.py analyze-customer --base D:\Claude\客户解决方案库-私有 --customer-id CUST-0001
```

生成信息缺口清单：

```powershell
python scripts/customer_library.py gaps --base D:\Claude\客户解决方案库-私有 --customer-id CUST-0001
```

根据产品/服务筛选潜在客户：

```powershell
python scripts/customer_library.py product-match --base D:\Claude\客户解决方案库-私有 --product-id PROD-001
```

生成本周经营看板：

```powershell
python scripts/customer_library.py dashboard --base D:\Claude\客户解决方案库-私有
```

### 4.6 从录入到洞察

录入只是第一步。真正有价值的日常用法是：

```text
使用 $customer-solution-library。
请分析 CUST-0001，输出客户深度分析、信息缺口和下一步跟进建议。
```

或者：

```text
使用 $customer-solution-library。
我准备推广 PROD-001，请筛选潜在客户，并说明匹配原因、风险点和建议动作。
```

或者：

```text
使用 $customer-solution-library。
请生成本周经营看板，列出最值得跟进的客户、缺少下一步动作的客户、可进入方案复核的客户。
```

这一步的目标不是让 Agent “多写一点总结”，而是让客户库回答经营问题：

- 谁现在最值得跟？
- 谁已经可以出方案？
- 谁还缺关键资料？
- 某个产品/服务适合哪些客户？
- 哪些客户风险较高，不能直接推进？
- 下一步最小动作是什么？

## 5. 与传统方案的区别和优势

### 5.1 与 Excel / 表格的区别

Excel 适合管理固定字段，例如姓名、电话、来源、阶段、跟进日期。

但它不擅长管理：

- 客户原话
- 多轮沟通变化
- 健康告知细节
- 方案推演过程
- 团队协作过程
- 服务复盘记录

客户管理库的优势是：既保留结构化字段，又能保存完整上下文。

### 5.2 与传统 CRM 的区别

传统 CRM 更关注销售流程：

```text
线索 → 跟进 → 成交 → 回访
```

客户管理库更关注客户理解和解决方案：

```text
信息 → 判断 → 匹配 → 画像 → 分析 → 方案 → 跟进 → 复盘
```

对比：

| 维度 | 传统 CRM | 客户管理库 |
|---|---|---|
| 核心目标 | 管销售流程 | 管客户理解和服务过程 |
| 最小单位 | 客户记录 | 客户信息事件 |
| 信息形态 | 表单字段 | Markdown + YAML + 事件流 |
| 上下文保存 | 较弱 | 较强 |
| AI 适配 | 需要额外改造 | 天然适合 Agent 读取和处理 |
| 客户分析 | 多依赖人工 | 可由 Agent 辅助生成 |
| 方案沉淀 | 较弱 | 可形成方案库和复盘库 |
| 同名风险 | 常靠人工判断 | 有身份锚点和防误并档规则 |
| 产品筛选 | 多依赖销售经验 | 可按产品画像反向筛客户 |
| 经营看板 | 多依赖人工维护 | 可自动生成可行动清单 |

### 5.3 与普通知识库的区别

普通知识库保存的是“我知道什么”。

客户管理库保存的是“这个客户发生了什么，以及我下一步该如何服务”。

所以它不是把客户资料塞进知识库，而是为客户服务过程设计了一套专门结构。

## 6. 推荐的日常节奏

每天：

```text
处理新入口
→ 判断价值
→ 匹配客户
→ 入档或待匹配
→ 设置下一步动作
```

每周：

```text
刷新索引
→ 检查待匹配客户
→ 生成跟进清单
→ 处理高价值客户
→ 生成本周经营看板
```

每月：

```text
生成数据质量报告
→ 清理低价值归档
→ 检查疑似重复客户
→ 复盘典型客户案例
→ 更新产品/服务画像
→ 生成产品潜在客户清单
```

---

## 7. 隐私和边界

不要把真实客户资料提交到公开仓库。

建议：

- 真实客户库单独保存。
- 高敏信息尽量脱敏。
- 文件名不要直接写完整真实身份。
- 团队协同时只共享必要摘要。
- 对客户可见内容和内部判断分开。
- 不确定的信息标记为待确认，不要写成事实。
- 涉及健康、法律、理赔、财务承诺时保持保守。

---

## 8. 一句话总结

这套客户管理库的本质是：

> 以客户信息事件为最小单位，用 Markdown 保存上下文，用结构化字段保持可检索，用 Agent 完成价值判断、客户匹配、洞察分析、产品筛选、方案生成和跟进复盘。

它不是为了多存资料，而是为了让客户信息真正变成可理解、可追踪、可协作、可复用的长期服务资产。
