# 对话入库：录音转写、聊天记录、口述记录

## 适用输入

以下材料都可以作为客户信息来源：

- 录音转写文字
- 微信/短信/邮件聊天记录
- 面谈纪要
- 用户口述的聊天经过
- 客户发来的资料说明

如果只有录音文件而没有转写文字，本 Skill 不直接处理音频；应先用语音转文字工具生成文本，再进入本流程。

## 基本原则

1. 对话是“证据来源”，不是最终结论。
2. 原话、事实、推断、待核实必须分开。
3. 先身份匹配，后更新档案。
4. 同名不能直接并档。
5. 主档案只写稳定摘要，细节留在沟通记录。

## 对话记录 YAML

```yaml
---
type: customer_interaction
interaction_id: INT-20260711-001
customer_id:
possible_customer_ids: []
match_status: unmatched
match_confidence: low
conversation_date: 2026-07-11
record_created: 2026-07-11
source_type: audio_transcript
source_quality: medium
participants:
  - self
  - customer
privacy_level: high
business_line: []
update_status: draft
tags:
  - 对话入库
---
```

`source_type` 可选：

- `audio_transcript`
- `chat_log`
- `manual_summary`
- `meeting_note`
- `email`
- `other`

`source_quality` 可选：

- `high`：逐字稿清楚，有时间、说话人
- `medium`：大意清楚，但有少量缺漏
- `low`：转写混乱、说话人不清、信息不完整

`match_status` 可选：

- `matched`
- `candidate`
- `unmatched`
- `new_customer_likely`
- `conflict`

## 身份匹配流程

先提取身份锚点：

| 锚点 | 示例 |
|---|---|
| 姓名/称呼 | 张先生、王总 |
| 联系方式线索 | 手机后四位、微信昵称 |
| 来源 | 李姐转介绍、直播间咨询 |
| 城市/地区 | 杭州、上海 |
| 公司/职业 | 个体老板、老师、医生 |
| 家庭结构 | 已婚、一孩、父母同住 |
| 历史事件 | 上次说过体检异常、之前整理过保单 |
| 业务特征 | 问重疾险、问知识库搭建 |
| 时间线 | 上周见过、去年买过 |

匹配等级：

```text
match_high：姓名/别名 + 至少两个强锚点一致
match_medium：姓名/别名 + 一个强锚点一致，或多个弱锚点一致
match_low：只有姓名或只有模糊特征
new_customer_likely：没有旧档案匹配，且信息足以建 L0/L1 档案
conflict：关键锚点冲突
```

强锚点：

- customer_id
- 脱敏联系方式
- 来源人
- 公司/职业与城市组合
- 家庭结构与历史事件组合
- 旧档案中独有事件

硬规则：

- 只有姓名相同：不得并档。
- 对话时间不同：不能作为并档依据，只能作为记录排序依据。
- 用户明确说“这是 CUST-0003 那位客户”：可按高置信处理。
- 出现冲突时，创建待匹配记录，不更新旧档案。

## 摘录结构

从对话中提取以下内容：

```markdown

## 1. 来源信息

- 来源类型：
- 对话时间：
- 转写质量：
- 参与人：

## 2. 身份匹配

- 可能客户：
- 匹配等级：
- 匹配依据：
- 冲突点：
- 建议处理：

## 3. 客户明确事实

## 4. 客户原话

## 5. 显性需求

## 6. 隐性需求/可能顾虑

> 必须标注“推断依据”，不能写成事实。

## 7. 业务相关信息

### 保险相关

### 咨询/合作相关

### 其他

## 8. 待确认信息

## 9. 建议更新到主档案的字段

## 10. 建议新增/更新的业务模块

## 11. 下一步动作
```

## 入档规则

### 高置信匹配

可以执行：

1. 新建沟通记录。
2. 更新主档案摘要。
3. 更新业务模块。
4. 添加变更记录。
5. 刷新索引。

### 中置信匹配

先输出候选客户和匹配依据，请用户确认。

确认前只保存为：

```text
00-收件箱/待匹配-YYYY-MM-DD-客户称呼.md
```

### 低置信或冲突

不要更新任何已有客户。

保存为：

```text
00-收件箱/待匹配-YYYY-MM-DD-客户称呼.md
```

并输出需要用户确认的问题：

- 这是哪一位客户？
- 是否新建客户？
- 是否有手机号后四位/来源人/城市/业务线可辅助判断？

## 文字转述的处理

用户口述聊天经过也可以入库，但可信度默认低于原始聊天记录或逐字稿。

标记：

```yaml
source_type: manual_summary
source_quality: medium
```

处理规则：

- 用户明确说“客户说过”的，作为“转述事实”。
- 用户自己的判断，作为“观察/推断”。
- 需要客户确认的内容，列入“待确认信息”。

## 同名客户处理示例

输入：“今天和张先生聊了，他说孩子刚上小学，想看看重疾险。”

如果库里有两个张先生：

```markdown
找到多个可能客户：

1. CUST-0001｜张先生｜杭州｜已婚一孩｜之前问过医疗险
2. CUST-0012｜张先生｜上海｜企业主｜之前问过知识库服务

仅凭姓名和本次内容，不能安全判断是哪一位。建议确认：城市、来源人、手机号后四位或是否就是之前问医疗险的张先生。
```

如果库里有一个张先生，且旧档案记录“已婚一孩、杭州、曾问医疗险”，则可以判定 `match_medium` 或 `match_high`，但仍要在沟通记录中保留来源。

## 不允许的行为

- 不要把转写中的模糊词直接写成确定结论。
- 不要自动合并同名客户。
- 不要覆盖旧方案，应追加“本次对话后调整”。
- 不要把内部判断直接生成给客户看的话。
- 不要保存未脱敏的敏感资料到公开仓库。
