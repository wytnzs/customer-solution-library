# 客户洞察与深度分析规则

## 目标

客户分析不能停留在“摘要”。每次分析都要尽量产出可执行判断：

```text
事实 → 推断 → 洞察 → 信息缺口 → 下一步动作
```

## 客户洞察卡

客户洞察卡是客户信息事件之后的第二层分析单位。

客户信息事件回答“发生了什么”；客户洞察卡回答“这意味着什么、下一步该怎么做”。

洞察类型：

| 类型 | 说明 |
|---|---|
| 需求洞察 | 客户明确或隐含需要解决的问题 |
| 风险洞察 | 健康、核保、理赔、法律、隐私、预算、交付等风险 |
| 机会洞察 | 产品、服务、转介绍、合作、内容、复盘机会 |
| 顾虑洞察 | 客户犹豫、抗拒、担心、不信任的原因 |
| 信息缺口 | 形成方案前必须补齐的信息 |
| 跟进洞察 | 当前最小下一步动作 |

每条洞察必须尽量包含：

```yaml
type: customer_insight
customer_id:
insight_type:
conclusion:
evidence:
confidence: high | medium | low
status: pending_review | actionable | handled | expired
related_products: []
action_suggestion:
```

## 分析三层

做客户分析时必须区分：

| 层级 | 要求 |
|---|---|
| 事实 | 客户明确说过、文件记录过、事件流中有证据 |
| 推断 | 根据事实形成的判断，必须说明依据 |
| 待确认 | 影响方案或行动但尚未确认的信息 |

不要把推断写成事实。涉及健康、理赔、法律、财务承诺时必须保守。

## 深度分析输出

默认输出结构：

```markdown
# 客户深度分析：<客户>

## 结论先行

## 当前状态

## 关键需求

## 关键风险

## 潜在机会

## 关键顾虑

## 信息缺口

## 证据摘录

## 下一步建议
```

## 信息缺口判断

信息缺口不是“资料越多越好”，而是判断：

```text
缺少哪些信息，会导致现在无法形成稳定方案或行动？
```

保险客户常见缺口：

- 已有保单
- 家庭责任与收入结构
- 健康异常详情
- 预算/缴费承受能力
- 保障优先级
- 客户真实顾虑

咨询/服务客户常见缺口：

- 明确目标
- 当前卡点
- 预算或投入边界
- 决策链条
- 可交付成果
- 时间要求

## 可执行命令

生成客户深度分析：

```powershell
python scripts/customer_library.py analyze-customer --base <客户库路径> --customer-id CUST-0001
```

生成信息缺口清单：

```powershell
python scripts/customer_library.py gaps --base <客户库路径> --customer-id CUST-0001
```

生成本周经营看板：

```powershell
python scripts/customer_library.py dashboard --base <客户库路径>
```

## 使用原则

1. 用真实姓名指定客户最直接（内部编号同样可用）。
2. 只有姓名或称呼时，先做身份匹配，不要直接写入或分析。
3. 客户深度分析应读取主档案、事件流、业务模块和最近方案。
4. 分析结果默认是内部版，不直接发给客户。
5. 给客户看的内容必须另行转成客户可读版话术。
